# Smooth secure online play — 1.15

## What caused the jitter

The guest already moved locally, but each authoritative snapshot unconditionally reset its car and replayed input, even for sub-centimetre rounding differences. Presentation smoothed those errors, so repeatedly restarting the correction path could look like the server was dragging the car back. The old remote-input receiver also acknowledged the **latest received** sequence while coalescing movement; it did not mean that every acknowledged movement frame had been simulated. Replaying against that acknowledgement does not consistently compare equivalent moments.

Both Node and the Cloudflare adapter share [game-service.mjs](../server/game-service.mjs). The dedicated server now consumes sequenced inputs once per 120 Hz tick and acknowledges the **last simulated frame**. The client saves predicted states at each sequence. It compares authority with the predicted state **at that acknowledgement**, not the much newer car shown on screen. Small differences keep the local trajectory. Meaningful differences restore authoritative movement, replay all unacknowledged input and retain a decaying visual error offset. This preserves new input immediately while gradually moving the picture towards the corrected result.

## Implementation

1. [network-state.js](../dist/network-state.js): a bounded 120-frame prediction history; 6 cm position, 0.3 m/s velocity, 0.025 rad orientation and 0.2 rad/s angular-velocity thresholds; discrete movement/respawn state changes also reconcile. Authoritative scores/stats still synchronize when motion correction is skipped. Large teleports, phase changes and respawns reset presentation deliberately. Ordinary corrections preserve the rendered pose at receipt and decay at rate 18/s. Practice uses the same unlimited-boost prediction as its server.
2. [inputs.mjs](../server/inputs.mjs): bounded input sequencing at fixed server time, duplicate/old-frame rejection, short missing-frame fill from held input, stale input neutralization and acknowledgement on consumption. A client cannot advance the server with its own delta time or position.
3. [session.mjs](../server/session.mjs) and [server-options.js](../dist/server-options.js): shared mode contract, server-owned driving seats, all five modes, bots, spectators/owner transfer, chat, rematch consent and 20-second reconnect to authenticated seats. Free play/training practice actions and drill metadata are authoritative.
4. [matchmaking.mjs](../server/matchmaking.mjs): bounded server queue, partitioned modes/preferences, a server-clock 60-second deadline and server bot fill; practice/custom sessions create immediately. Cancellation removes waiting players. [server-matchmaking.js](../dist/server-matchmaking.js) connects that lifecycle to the existing menu.
5. [auth.mjs](../server/auth.mjs), [server-auth.js](../dist/server-auth.js) and [server/index.mjs](../server/index.mjs): server-issued guest identity, one-use socket tickets, HTTPS/WSS, origin/build/message/rate/seat validation and protected lobby commands. No application secret/packet/profile logging. TLS material is supplied externally; no account keys are embedded.
6. [render.yaml](../render.yaml), [Dockerfile](../Dockerfile) and [server setup](dedicated-server.md): one free Singapore service or a portable direct-TLS container. New server-served pages default to their own endpoint unless the player already saved a preference. Static-host pages let the player enter a public server URL.

Remote cars retain a timestamped **85–220 ms adaptive interpolation buffer**, up to **120 ms extrapolation**, old snapshot rejection and a non-reversing presentation clock. Fixed-rate snapshots carry sequence numbers, elapsed server time and per-driver input acknowledgements. This intentionally trades a short remote presentation delay for smoother motion. The local car does not use that interpolation buffer.

## Automated evidence and limits

`npm run check` passes browser, script and server syntax checks. All **279 tests pass**, including 10 real workerd tests for the no-card hosting adapter. Both hosting adapters are covered by real HTTPS/WSS driving and reconnect checks, with certificate verification enabled. `npm test` includes real HTTPS/WSS multi-client sessions with a temporary explicitly trusted certificate; TLS verification stays enabled. Integration coverage includes every mode, bot filling at exactly 60 seconds, cancellation, two-player matching, spectators, authoritative practice commands, forbidden owner operations, guest impersonation attempts, one-use tickets, unauthenticated requests, reconnects, rematches, eight-person rooms and ignoring client-authored state/score/time.

The deterministic network harness runs 8-second steering and changing-input/jump/flip trials at **50/100/150 ms RTT**, with **3% dropped application updates**, arrival jitter and reordering. The initial steady-driving results accepted 228–230 snapshots, skipped 226–228 insignificant corrections and used only two movement reconciliations after initialization. Receiving a snapshot introduced **no position discontinuity beyond floating-point rounding**. The largest fixed-step movement was about 0.13 m in the changing-input trials; pending inputs stayed below 40. A separate regression checks full 600 ms input replay and one-way world age.

These are synthetic physics/presentation and real loopback transport checks, not a measured WAN trial or a guarantee that every browser/GPU looks smooth. Application-update loss is also different from TCP-level packet loss: WSS retransmits, so real loss can cause head-of-line stalls. The Cloudflare adapter additionally passes real local workerd/HTTPS/WSS tests for all modes, matchmaking, chat, reconnects and limits. See the [no-card hosting guide](cloudflare-free.md). The free public server has not been provisioned without the owner's account; actual Singapore/OCE latency, browser rendering and two independent houses must still be tested. Follow the explicit [two-PC/cross-network checklist](dedicated-server.md#two-pc-and-cross-network-checks).

Every browser and server must run **boost-circuit-1.15.0**. A running 1.13/1.14 page cannot join a 1.15 server. Deployment restarts intentionally end in-memory rooms; this release does not pretend that a dead process can reconnect to lost match state.
